# Notion management in Remote Commander Control Center

This feature extends the existing [Native Notion Engine](./NOTION_NATIVE_ENGINE.md) in the existing opt-in feature branch. It uses Commander Core's official Notion REST client; it does **not** share or extract the ChatGPT Notion connector's token, the separately authorized hosted Notion MCP token, browser cookies, or any existing Commander profile secrets.

## Windows and Linux

- **Windows:** Open Remote Commander Control Center, select **Notion Connection**. Alternatively launch `RemoteCommander.exe --notion-connect`. Choose the exact Commander profile; connection status, live verify, masked token enrollment and explicitly confirmed local disconnect are in this same dialog. The token is submitted to the local importer via a child process's stdin, not command-line arguments.
- **Linux:** Open the existing GTK4 Control Center and select **Notion** in its left sidebar. This page has per-profile connection status, live verify, masked token enrollment, and an explicit check-box required before local disconnect. The only credential-bearing operation sends the token to `tools/notion-pat-import.mjs` through stdin, not shell or argv. The existing monitoring, workflow and profile screens remain read-only.
- **Headless Linux or Windows:** `node tools/notion-pat-import.mjs --status --profile default`, `node tools/notion-pat-import.mjs --verify --profile default`, `node tools/notion-pat-import.mjs --disconnect --confirm-disconnect --profile default`. Enrollment requires an owner-local masked input (e.g., GUI or private stdin pipe) with `--token-stdin --profile <profile>`. Never paste a credential into ChatGPT or command-line arguments.

The importer **only reports bounded fixed success/status markers**. No tokens or other credentials may be returned in tool results, logs, status labels or diagnostics. Each profile has an independently keyed local REST credential in Windows DPAPI or the Linux libsecret keyring. The local disconnect operation deletes only that profile's REST credential; it **does not revoke** the underlying token at Notion, delete pages, change another profile, or sign out of hosted Notion MCP. To revoke a compromised token, use the official Notion developer portal.

`--verify` performs a real read-only `GET /v1/users/me` using the already-stored credential and does not change any authorization state. `--disconnect` requires an explicit `--confirm-disconnect` action; mixed CLI modes, invalid profile names, missing vault access and unsupported actions fail closed. The core MCP tools do not expose an autonomous disconnect or arbitrary token-handling primitive.

## Installation and QA

The Windows executable is built from `desktop/RemoteCommanderDashboard/RemoteCommanderDashboard.csproj`, with its Notion management form compiled into the existing application. The GTK4 UI resides under `desktop/linux-control-center` and resolves the same packaged Node importer relative to the application root. Users must have Node.js available, and Linux must have a usable unlocked libsecret keyring for REST credential storage.

The `.github/workflows/gtk-control-center-r32.yml` suite discovers `test_notion_panel.py` automatically, and the standard Windows R34/native UI and Node test workflows cover their respective backends. Native GUI observation and multi-DPI/Wayland owner acceptance remain independent release gates. Functional tests use synthetic credentials and mocked API responses; they must not delete or replace an owner's existing credential.

### Linux Control Center packaging and updater integration (candidate, 2026-10-22)

- `desktop/linux-control-center/install_user.py --stage` generates a fresh **owner-private** review directory under the OS user's fixed `~/.local/share` root and prints `LINUX_CONTROL_CENTER_STAGE_PASS <path>`. It stages **inert** GUI bytes and launcher; an arbitrary external `--stage-dir` is intentionally unsupported to remove tainted destination paths. No live GUI, Core, services, desktop input or credentials are modified.
- Explicit `--install` transactionally installs or upgrades the existing GTK GUI under the OS uid's fixed `~/.local/share/remote-commander-control-center` and updates its existing desktop launcher. An `XDG_DATA_HOME` override that changes the install root is **rejected** (including a custom owner-home descendant), preventing environment-driven migration. The old directory, including original user receipts, is retained under an owner-private `.rc-cc-backup-*` rollback directory; conflicting launchers, symlinks and unsafe paths are rejected; repeated identical installation is a no-op.
- **TOCTOU hardening in dependent PR #85:** GUI `--install` now retains the random `tempfile.mkdtemp` stage and rollback reservations through rename, instead of deleting and reclaiming their pathnames, and creates the launcher staging file with `tempfile.mkstemp` (exclusive unpredictable name, 0600) rather than a predictable `.staged` path. An additional regression protects an unrelated symlink target and verifies no reservation release. This narrows name-replacement races but is **not** a proof against same-UID adversarial mutation of every filesystem ancestor or an fd-relative `openat` audit. Native Linux isolated suite at this change: **38/38 Python PASS, 2/2 Node PASS**, `bash -n` PASS; the exact modified SHA still requires hosted CI and scoped CodeQL requalification.
- Deployed standalone GTK files now locate the Core Notion importer at `~/.local/share/ChatGPTRemoteCommander/tools/notion-pat-import.mjs`, with the managed user-local Node runtime preferred. The source checkout resolution remains only an isolated development fallback. Missing installed Core importer displays a bounded failure; there is no credential reuse.
- `auto-update-linux.sh` includes an opt-in-existing-installation GUI upgrade step **after** accepted Core promotion, and a maintenance step for an already-current Core. It is inactive in `--no-promote` mode and when no existing Control Center launcher/app is found. If GUI packaging fails, the Core update can remain healthy while a separate `LINUX_CONTROL_CENTER_UPGRADE_DEFER_*` receipt records the GUI as not accepted. Nothing automatically enables Auto-update on machines where it is disabled.
- Isolated QA on aliemad-Labtop used SHA-256-identical staged files: Python GTK/installer/Notion tests **31/31 PASS**; native Linux Bash updater tests **2/2 PASS** and `bash -n` PASS. Explicit staged package PASS, and the installed desktop launcher's hash was unchanged. Tests included rollback on failed launcher update, symlink/desktop-entry collision, no-promotion and idempotence. This is **not** a live GTK/Wayland owner acceptance, installer deployment to users, or general-fleet update.
- **Linux auto-update schedule candidate:** `stage_update_timer.py --core <installed-core> --stage-dir <new-private-dir>` generates an inert owner-local systemd service and daily randomized timer. It requires an existing legitimate Core updater, rejects symlinks/unsafe paths, neither installs nor enables units, and does not touch any real user's timers. A future owner-approved setup workflow must review the staged units, install them explicitly, and confirm timer execution before claiming automatic fleet updates. Three new isolated Linux fixture tests PASS; full Python suite **34/34 PASS**.
- Stable Release and deployment remain gated on exact commit hosted CI, cross-product integration, security/reviewer approval and verified native GUI/rollback. Current public upstream stable tag checked on 2026-10-22 was `v0.10.20`; `0.10.25`/Notion are not public stable. User-enabled updater cadence on the actual fleet is not established.

All of this stays **Draft / NoPromote** until independent review, CodeQL compatibility, cross-product integration checks and explicitly authorized owner acceptance. The Notion API is not the authoritative release gate or project control-plane authority.
